# MotorPulse mixed-motor dataset guide

**Version:** 1.0  
**Created:** 26 November 2026  
**Files:** [synthetic feature dataset](./motorpulse_mixed_motor_synthetic_v1.csv), [real capture template](./motorpulse_mixed_motor_real_capture_template.csv), and [reproducible generator](./generate_motorpulse_synthetic_dataset.py).

For a plain-language, step-by-step explanation of raw readings, feature calculations, labels, and per-motor baselines, see the [feature-engineering beginner guide](./MOTORPULSE_FEATURE_ENGINEERING_BEGINNER_GUIDE.md).

## What this dataset is and is not

The synthetic file contains **1,800 illustrative feature windows** spanning five motor families—induction, PMSM, BLDC, brushed DC, and stepper—with three simulated asset profiles per family. It includes healthy-like windows and deliberately generated vibration, thermal, current, operating-condition, and sensor-quality scenarios.

**None of the rows are physical measurements.** The motor values, features, conditions, and scenario labels are generated by simple assumptions and random variation. They are useful for testing CSV ingestion, UI display, feature pipelines, schema validation, and ML workflow code. They are **not suitable evidence of real-world fault-detection accuracy**, not a source of real motor baselines, and not a validated fault-classification training set. In particular:

- `scenario_label` describes the synthetic rule applied by the script; it is not a technician-confirmed diagnosis.
- `fault_status` is `not_assessed_synthetic` for every supplied row. The synthetic generator does not determine real fault vs non-fault.
- `fault_type_confirmed` is always `not_assessed_synthetic`.
- Do not report accuracy, recall, expected faults, failure risk, or savings from these rows as if they were measured on real motors.
- The illustrative values are not tied to the MotorPulse ESP32, calibrated sensor, actual nameplates, or any industrial installation.
- The 100 Hz vibration profile is intentionally aligned to the current low-frequency MotorPulse demo only as an example schema; it does not represent high-frequency bearing diagnostics.

Use the real capture template for real measurements. Keep raw samples in a time-series/Parquet or equivalent store and use the CSV as a **one-row-per-window feature table**. The template is only a header; its cells must be filled from real, timestamped acquisition and feature calculations.

Scenario groups are `synthetic_healthy`, `synthetic_vibration_deviation`, `synthetic_thermal_deviation`, `synthetic_current_deviation`, `synthetic_operating_change`, and `synthetic_sensor_quality_issue`. They are intentionally balanced for demonstration and **do not reflect industrial failure prevalence**.

## Data pipeline and collection protocol for real data

1. **Register the asset.** A technician records asset ID, motor construction, drive, driven equipment, and verified nameplate values. Record `unknown` in the asset registry when unverified; do not infer rated values from a model.
2. **Register the instrumentation.** Record sensor serial/model, location/orientation, mounting, calibration, range, filter, firmware, units, and acquisition cadence. Use a vibration sensor/sample rate with enough bandwidth for the intended monitoring task.
3. **Capture raw sensor values.** Keep vibration samples with device sample times/sequence numbers and the measured sample rate. Temperature, current, RPM, and drive/process readings each retain their own measurement timestamps/cadence. Do not copy a slow sensor value into many raw samples and pretend those are independent measurements.
4. **Build a window.** Group continuous vibration readings into a documented window, for example 1.28 s for the current 128-at-100-Hz demo. Reject or flag gaps, clipping, stale sensors, miscalibration, and time misalignment. Ensure the motor state is steady if the baseline is for steady running.
5. **Calculate features from raw samples.** Calculate vibration statistics from the raw acceleration window; derive temperature rise/trends only from time-aligned readings; use the actual current measurement resolution. Record the formulas/schema version. Do not calculate spectral-current features from one-second RMS current.
6. **Join operating context.** Associate measured RPM, run/stop/transient state, drive mode/frequency, and load/process readings valid for that window. Prefer measured shaft speed over a setpoint.
7. **Label with evidence.** Keep a window `unknown` until reviewed. Mark healthy only after human verification. A fault label requires independent inspection/maintenance evidence. Record sensor problems and process/operating changes separately from faults.
8. **Separate sources and evaluation splits.** Keep real, simulated, public, and test-rig records distinguishable. Split ML evaluation by whole asset and/or acquisition session, not by random adjacent windows. For a real baseline, train on verified healthy windows from that same asset and relevant operating regime.

### Motor-family treatment

The sensor does not identify a motor family. `motor_type`, `drive_type`, and `driven_equipment` are metadata supplied from a verified asset record. The same basic vibration/temperature features may be available across families, but each asset has its own baseline. Add conditional features only when the required sensor and signal quality exist:

- **Induction:** actual speed and drive/supply context; electrical slip/sideband analysis requires a suitable high-rate electrical waveform and supporting motor parameters.
- **VFD-driven:** actual shaft RPM and drive state are required to compare variable-speed vibration fairly.
- **PMSM / BLDC:** capture controller/commutation and actual speed context where available; do not assume induction-motor slip features apply.
- **Brushed DC:** controller/PWM state helps interpret current ripple; record current sensor position and whether it measures motor or supply current.
- **Stepper:** controller command and position/encoder feedback are needed to substantiate missed-step/following-error features.
- **Servo:** drive-supplied torque/current/following error can be added as separate telemetry, with source and units; an accelerometer does not measure those.

For these mixed types, first use **per-asset/per-regime anomaly detection**. A pooled family model is a later option only when there are compatible sensor configurations and enough diverse, verified real data. A model must return out-of-coverage/unknown for unsupported motor or operating conditions.

## Column-by-column dictionary

One row represents one time window from one asset. Blank numeric values mean **not measured or invalid**, never zero. In the synthetic dataset, blank sensor features occur in the deliberately invalid sensor-quality scenario.

| Column | Type / units | How to capture or calculate | Important interpretation |
|---|---|---|---|
| `window_id` | string | Unique ID assigned to the feature-window record by the collector. | Must remain stable so a feature row can be traced to raw samples. |
| `session_id` | string | ID for one acquisition/operating session. Assign when a capture run starts. | Group by session for train/test splitting; session IDs in this file are synthetic. |
| `recorded_at_utc` | ISO-8601 UTC | Real data: start timestamp of the window, derived from synchronized acquisition timestamps. Keep device monotonic/sample time too in raw storage. | Synthetic rows use generated timestamps and are not wall-clock observations. |
| `data_source` | category | Set by the acquisition pipeline: `real`, `test_rig`, `public_dataset`, or `synthetic`; retain finer provenance if available. | Every supplied dataset row says `synthetic_generator_v1`. |
| `asset_id` | string | Stable ID from the asset registry. | One physical motor must retain its ID across sessions. |
| `motor_type` | category | Technician-verified nameplate/manufacturer data: `induction`, `pmsm`, `bldc`, `brushed_dc`, `stepper`, or `other/unknown`. | Metadata, not a sensor inference. Do not train from synthetic type labels as if verified in the field. |
| `drive_type` | category | Read from verified installation information or approved drive interface: e.g. `vfd`, `servo_drive`, `pwm_controller`, `stepper_driver`, `direct_on_line`. | A drive change/configuration change can invalidate operating comparisons. |
| `driven_equipment` | category | Technician-selected equipment: pump, fan, conveyor, axis, indexer, etc. | Process/load changes can alter motor-mounted signals. |
| `rated_power_kw` | number, kW | Transcribe from verified nameplate or manufacturer record. | Not inferred from current; leave unknown if not verified. |
| `supply_phase_count` | integer/category | Record the electrical supply/drive input phases from the nameplate or approved documentation. | For electronically commutated motors, distinguish supply phases from motor winding phases in a richer asset schema. This simplified field is illustrative. |
| `rated_voltage_v` | number, V | Verified nameplate/drive configuration. | Do not assume it equals measured voltage. |
| `rated_speed_rpm` | number, rpm | Verified nameplate/manufacturer value. | Not the same as actual measured shaft RPM. |
| `sensor_profile` | string/category | Capture sensor type/model, range, bandwidth, sampling configuration, and other metadata in the device registry; this column is a concise profile ID. | Real records should reference a versioned sensor registry. The supplied profile is simulated. |
| `sensor_mount_location` | string/category | Technician records bearing end/location, orientation/axes, and mounting method in the installation record. | Remounting or moving the sensor can change the baseline. |
| `sample_rate_hz` | number, samples/s | Measured acquisition cadence from device timestamps/DAQ clock, not only a requested setting. | For irregular sampling, store timestamps and quality statistics; do not treat nominal rate as proof of uniform samples. |
| `window_duration_s` | number, seconds | `number_of_samples / actual_sample_rate_hz` for uniform vibration samples; otherwise use first-to-last sample times and flag irregularity. | Frequency resolution depends on duration and processing. |
| `actual_rpm` | number, rpm | Tachometer/encoder or trusted measured drive feedback, time-aligned with window. | A command/setpoint is not necessarily shaft speed. Synthetic values are modeled. |
| `load_pct` | number, percent | Use a calibrated torque/load measurement, validated drive load estimate, or documented process proxy with method recorded. | If unavailable, leave blank; do not invent load from motor current without validation. |
| `run_state` | category | State machine from drive/status signal or reliable operator/system event: `stopped`, `starting`, `steady`, `stopping`, etc. | Exclude or separately model transients; `steady` in generated data is a scenario assumption. |
| `accel_x_rms_m_s2` | number, m/s² | From calibrated X acceleration samples after the documented preprocessing/filtering; `sqrt(mean(x²))` for AC-coupled/demeaned dynamic vibration. State explicitly whether the mean is removed. | This dataset simulates feature values. The current API does not calculate per-axis RMS separately. |
| `accel_y_rms_m_s2` | number, m/s² | Same calculation for Y samples. | Same limitations as X. |
| `accel_z_rms_m_s2` | number, m/s² | Same calculation for Z samples. | Same limitations as X. |
| `accel_x_peak_abs_m_s2` | number, m/s² | `max(abs(x_demeaned_samples))` within window. | Sensitive to spikes, clipping, and sensor mounting. |
| `accel_y_peak_abs_m_s2` | number, m/s² | `max(abs(y_demeaned_samples))` within window. | Same limitations as X. |
| `accel_z_peak_abs_m_s2` | number, m/s² | `max(abs(z_demeaned_samples))` within window. | Same limitations as X. |
| `accel_vector_rms_m_s2` | number, m/s² | For synchronized axes, `sqrt(mean(x² + y² + z²))` after the documented per-axis offset removal. | This matches the general calculation in the current edge API. |
| `accel_peak_to_peak_max_m_s2` | number, m/s² | `max(ptp(x), ptp(y), ptp(z))` where `ptp(axis) = max(axis)-min(axis)` on the window. | Current API computes this maximum. It hides which axis was largest; retain per-axis values in a future schema if useful. |
| `accel_crest_factor_max` | dimensionless | For each axis calculate `max(abs(axis_demeaned))/RMS(axis_demeaned)`; take the maximum over valid axes. | Undefined when RMS is zero/invalid. Calculate from raw samples in real capture; generated values are illustrative. |
| `dominant_frequency_hz` | number, Hz | From a documented windowed FFT/PSD on each axis, exclude DC, and select the frequency of the strongest valid spectral peak. | Current API chooses a strongest FFT bin without windowing/PSD calibration; one peak is not a fault diagnosis. |
| `temperature_c` | number, °C | Read from the identified temperature sensor and preserve its own timestamp. | DS18B20-on-casing is surface temperature, not winding temperature. Do not repeat one slow measurement as fresh samples. |
| `ambient_temperature_c` | number, °C | Separate ambient sensor at a representative location, timestamped independently. | Recommended additional measurement; not part of current MotorPulse telemetry. |
| `temperature_rise_c` | number, °C | `temperature_c - ambient_temperature_c` after time alignment. | Do not calculate if either value is missing or not time-aligned. |
| `current_rms_a` | number, A | From a calibrated current sensor/drive telemetry over the stated interval. For raw waveform: `sqrt(mean(i²))`; store sensor placement, phases, interval, and method. | Current MotorPulse ACS712 field is one-second RMS. It is not a raw waveform and cannot support detailed current-spectrum analysis. |
| `quality_status` | category | Collector decision based on sample gaps/jitter, clipping/saturation, stale sensors, calibration, timestamp alignment, and plausibility checks. | Use distinct statuses such as `valid`, `incomplete`, `sensor_fault`, `stale_context`; invalid samples should not receive a healthy label. |
| `scenario_label` | category | Synthetic file: assigned by a generator rule. Real file: keep as `unknown` unless the goal is a specific verified event label and review process exists. | Supplied values are scenario labels only, not fault diagnosis. |
| `fault_status` | category | For real data, assign `confirmed_fault` or `confirmed_no_fault` only after an independent inspection/maintenance outcome is linked to the capture. Use `unknown` while unreviewed or inconclusive. | Synthetic rows all say `not_assessed_synthetic`; no fault/non-fault target is present in this generated data. |
| `fault_type_confirmed` | category | Set a specific type only after independent inspection evidence, such as a confirmed bearing fault; otherwise use `unknown`/`not_assessed`. | Synthetic records all say `not_assessed_synthetic`; never treat them as confirmed faults. |
| `label_source` | string/category | Who/what created the label, with reviewer and evidence IDs stored in the production label table. | Synthetic rows say `synthetic_generator_rule`. |
| `split_group_asset_id` | string | Copy the asset ID for grouping held-out train/validation/test splits. Real model evaluation should group by physical asset and often session/time as well. | Prevents adjacent windows from the same asset appearing on both sides of a test split. |

### Feature formulas and implementation notes

For a real three-axis vibration window of `N` calibrated samples:

```text
x_rms = sqrt(mean(x[n]^2))                  # after documented mean removal
vector_rms = sqrt(mean(x[n]^2+y[n]^2+z[n]^2))
peak_to_peak_axis = max(axis) - min(axis)
peak_abs_axis = max(abs(axis))
crest_factor_axis = peak_abs_axis / axis_rms
frequency_bin_spacing_hz = sample_rate_hz / N
nyquist_hz = sample_rate_hz / 2
temperature_rise_c = temperature_c - ambient_temperature_c
current_rms_a = sqrt(mean(current_sample[n]^2))  # only if raw current samples exist
```

Use consistent preprocessing, calibration, anti-alias filtering, windowing, and unit conversion. Store feature schema/software version so old and new features are not mixed silently. The supplied synthetic generator does **not** create raw waveforms and does not compute its features through these DSP formulas; it creates plausible-looking feature values directly from simple rules. Therefore the script is a dataset/schema fixture, not a physically faithful motor simulator.

## Recommended ML use

- **Safe immediate use:** validate CSV loading, null/quality handling, dashboard filters, schema validation, asset grouping, and end-to-end baseline/model code with visibly synthetic badges.
- **Synthetic scenario classification:** `scenario_label` can be used as the target only to test recognition of the six generator-created scenarios. It does not answer whether a physical motor has a fault.
- **Real binary fault classification:** use `fault_status` as the target only for independently reviewed real/test-rig examples with `confirmed_fault` or `confirmed_no_fault`; exclude `unknown` from supervised training. Train a separate `fault_type_confirmed` target only on confirmed fault examples with verified type.
- **Not suitable:** claiming performance on actual motors, deriving real healthy limits, fault diagnosis, or remaining-useful-life estimation.
- **Real baseline/anomaly use:** collect manually verified healthy windows per asset and operating regime, then test on later sessions from that asset.
- **Fault classifier:** collect safe real/test-rig recordings with independently confirmed labels and hold out complete motors/sessions. Include sensor issue, operating change, and unknown outcomes as separate cases.
- **Cross-motor evaluation:** use grouped splits by `split_group_asset_id`; do not random-split rows. Report performance per motor family and operating regime, plus overall values and out-of-coverage behavior.
- **Synthetic training caution:** models trained on this generator will learn generator conventions. If used to verify a pipeline, label the exercise “synthetic demonstration”; do not report the score as field accuracy.

## Reproducibility

From the project directory, run:

```powershell
python MotorPulsePoc\generate_motorpulse_synthetic_dataset.py
```

This recreates the deterministic synthetic feature dataset and the blank real-capture CSV header. The generator uses Python’s standard library only.
